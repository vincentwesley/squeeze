## Architecture and tooling

- **D1 Language: TypeScript, ES2022, no runtime dependencies.** The same core runs in Node (library + CLI) and the browser (web page). Typed arrays give predictable performance.
- **D2 Package name `@vins-atelier/squeeze`, CLI binary `squeeze`.** The bare `squeeze` name is taken on npm; the scope matches the studio name.
- **D3 Tooling:** `tsc` (TypeScript 7) for the library and type declarations, `esbuild` to bundle the CLI and the web page, `vitest` for tests, `biome` for lint + format (one fast tool instead of ESLint + Prettier). All dev-only.
- **D4 Whole-buffer API** (see B10): `deflateRaw/inflateRaw`, `zlibCompress/zlibDecompress`, `gzip/gunzip`, `encodePng/decodePng`. Inputs and outputs are `Uint8Array`.
- **D5 Errors:** every decoder failure throws `SqueezeError` with a stable `code` (e.g. `BAD_CRC`, `DISTANCE_TOO_FAR`). Fuzz tests assert that _nothing else_ is ever thrown.
- **D6 Inflate tables:** two-level lookup (9-bit primary for literals/lengths, 7-bit for distances, sub-tables for longer codes), like zlib. Code-set validation follows `inftrees.c` exactly so differential fuzzing agrees with zlib.
- **D7 Deflate levels:** 0 = stored; 1–3 greedy hash-chain matching; 4–9 lazy matching; parameters follow zlib's configuration table so levels mean the same thing. 10–12 = optimal parsing (B1) with 1, 5 and 15 cost-model iterations.
- **D8 Huffman code lengths:** package-merge (optimal under the 15-bit / 7-bit limits) instead of zlib's heuristic tree-flattening.
- **D9 Block splitting:** emit a block every 16 384 symbols _or_ earlier when the symbol statistics shift (simple observation-based splitter in the spirit of libdeflate), and for each block choose stored / fixed / dynamic by exact bit cost.
- **D10 Strict PNG decoder:** CRC checked on every chunk; unknown critical chunks rejected; chunk-order rules enforced (IHDR first, PLTE before IDAT, IDAT contiguous, IEND last); IHDR validated; trailing bytes after IEND ignored (as libpng does). Output is RGBA with 8 or 16 bits per channel, plus the raw decoded samples and palette.
- **D11 Corpora are downloaded, never committed:** `scripts/fetch-corpora.mjs` pins URL + SHA-256 and caches in `.cache/corpora`. Canterbury and Silesia have no stated licence, so they are not bundled anywhere (see RESEARCH.md).
- **D12 Web page bundles no third-party test files.** Sample text is written for this project; the sample image is generated procedurally in the browser. (PngSuite would be allowed but is not needed.)
- **D13 Benchmarks:** `scripts/bench.mjs` runs Squeeze and Node's built-in zlib in the same Node process on the same files, median of N runs, and writes `bench/results.json` + `docs/BENCHMARKS.md`.
- **D14 Git workflow:** the session may push only to `claude/squeeze-compression-aypkk6`. All work goes there; one pull request at the end describes the project.

## Decisions made while building

- **D15 gzip trailing data.** After a member, a `0x00` byte starts padding and ends the file; any other non-gzip bytes throw `TRAILING_DATA` unless `allowTrailingData` is set. This is exactly the rule in Node's zlib binding; the differential fuzzer found the first version (which required _all_ trailing bytes to be zero) disagreed with it.
- **D16 tRNS colour keys keep their colour.** For greyscale/truecolour images with a tRNS key, Squeeze sets alpha to 0 and leaves RGB as stored (the spec only defines alpha). pngjs also zeroes RGB; the PngSuite test therefore compares RGB only where alpha is non-zero, and says so.
- **D17 Optimal-parse speed limits.** Collecting every match at every position made level 12 take 10 s on `ptt5`. Two zlib-style limits fixed it without measurable ratio loss: a match of 258 bytes is taken directly (its interior is not searched), and once a 32-byte match is found the remaining chain budget is quartered. A "skip most long lengths in the DP" idea was tried and reverted: the DP was not the bottleneck.
- **D18 Hot-loop variables are never captured by closures.** The inflater's output buffer and position were captured by a `grow` closure, which forces V8 to keep them in a heap context; making `grow` a plain function and refilling the bit buffer only when fewer than 15 bits remain raised inflate speed by about 60%.
- **D19 Strict PNG decoding.** Squeeze requires IEND, consecutive IDATs, PLTE before IDAT, correct CRCs on every chunk (ancillary too), the exact image-data length and in-range palette indices; unknown _critical_ chunks are rejected, unknown ancillary chunks skipped. Bytes after IEND are ignored, as libpng does.
- **D20 Dev tooling needs Node 22, runtime needs Node 20.** Vitest 5 requires Node ≥ 22.12, so CI tests on 22 and 24 and runs the built CLI on Node 20 in a separate smoke job.
- **D21 CLI safety defaults.** `decompress` caps output at 1 GiB (`--max-output` raises it) and never overwrites files without `--force`, so a zip bomb or a typo cannot fill a disk or destroy data.
- **D22 Web page work happens in a Web Worker,** so level 12 on a large paste never freezes the page. The text view draws at most 24 000 bytes (canvas, not DOM, so thousands of arcs stay fast); the levels comparison uses at most 256 KiB.
- **D23 The web PNG view shows the optimiser's result,** not the default encoder's: on the sample image the default min-sum heuristic lost to "no filter", and showing a non-best file next to a "smallest" label would mislead.
- **D24 Single pull request.** The session can push only to its working branch, so all milestones are commits on that branch and one PR describes the whole project (per the brief).
- **D25 Close the project at 1.0.0.** Squeeze is a secondary portfolio project, so the scope is frozen at the brief plus release polish. `docs/ROADMAP.md` holds the definition of done, the maintenance policy (bug and security fixes only) and the list of ideas deliberately not planned.
- **D26 No routine dependency PRs.** Dependabot version updates are set to `open-pull-requests-limit: 0`. Dev-tool bumps add maintenance without changing the product, while security alerts and security updates keep working independently of that file.
- **D27 README leads with the product.** Screenshots of the web page (shrunk with Squeeze's own PNG optimiser) and the live demo link come first, followed by the results table.
